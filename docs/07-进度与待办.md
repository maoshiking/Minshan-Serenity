## 0. 地形迭代日志

### 第 17 轮 · 修掉"页面直接打不开"（完成）——上一轮埋的坑

**现象**：打开 `/terrain` 报 `createTerrainWorld: 缺少 DEM 高度场…`。
浏览器还附了一句"请检查是否启用硬件加速"（那是 `useThreeStage` 的通用兜底文案，与硬件无关）。

**根因是我上一轮埋的**：我把"没有 DEM 就抛错"写成了硬前置，但——

> `useThreeStage` 的 `setup` 是**同步**的（DOM 就绪时立刻建世界），
> 而 DEM 是**异步**取的（高度场 1 MB）。所以世界创建必然发生在数据到达**之前**。

于是每一次打开页面都会在数据到手之前把自己打死。

**修法：允许建一个空世界。**

```js
if (!currentOptions.demField?.data) {
  field = null      // 只有天空与光照，没有地形
  return
}
```

数据到了再由 `setDemField()` 灌进来。这不是"静默降级"——场景里根本没有假地形，
用户看到的是明确的"正在加载"。真正要防的"静默降级"是"退回一张程序化地形还当成真的"。

**连带修掉的两个真 bug**（都是这条流程暴露出来的）

| # | bug | 后果 |
|---|---|---|
| 1 | `size` 是**闭包 `const`**，DEM 到达后 `currentOptions.size` 变了但它没变 | "重置视角"按 120 取景而地形 1600 宽，角点 NDC 跑到 **15.6** |
| 2 | `rebuild` 只看 `currentOptions.size` 是否变化，不看 `demField.sizeMeters` | `setDemField(dem)` 之后尺寸仍是 120，相机 far 停在 960 m，地形被整片裁掉 |

第 1 条尤其值得记：`size` 在 14 处被引用（天空半径、光照位置、阴影相机范围、拾取距离、
默认取景），闭包捕获的是**变量本身**，所以改成 `let` 并在尺度变化时同步更新，
这些地方会一起跟上——比在每处单独改更不容易漏。

顺带把 `setResolution` 拆出来：调精度不再走 `rebuild`，
否则用户每换一档精度，视角就被重置一次。

**为什么既有自检全都没抓到**

因为**它们全都在构造时就把 DEM 传进去了**——那是一条第 15 轮引入、浏览器里并不存在的路径。
自检的流程与线上不一致，等于白测。

所以这轮把 `world-smoke.mjs` 改成**按真实装载顺序**跑：

```
先建空世界（无 DEM）  →  断言 field 为 null、不抛错
再 setDemField 灌入    →  断言尺寸变为 1600、相机 far 覆盖场景
再 setResolution       →  断言精度更新且**相机不被重置**
```

改完之后它立刻抓出了上面那两个 bug（先是 `far=960`，再是闭包 `size`）。
计数也从 66 涨到 **72**。

**新增 `scripts/check-preview-serve.mjs` 并并入 `npm run check`**

起一次 `vite preview`，验证**生产产物**能真正被服务出来，且三个地形数据文件可访问。
与 `check-dev-serve`（开发服务器 + 模块转换）互补——一个抓语法/导入错误，
一个抓"构建能过但页面跑不起来"。

**自检**：70 + 72 + 17 + 45 + dev server + 生产预览，全部通过。

### 第 16 轮 · 移除海岛内容 + 修复视角（完成）

**视角的两个 bug，其实是同一个根因**

用户反馈"地形太大，无法正常观察"，附了两张图：一张怼在树冠里、一张整片白。
查下来是**相机约束与雾的尺度还是按 120 单位海岛调的，而 DEM 场景是 1600 单位**：

| 参数 | 旧值（海岛尺度） | 在 1600 m 场景里的后果 | 新值 |
|---|---|---|---|
| `minDistance` | size × 0.35 = 560 | 镜头能贴到 560 m，而树只有 15 m 高 → 怼进树冠 | **120 m** |
| `maxDistance` | size × 4 = 6400 | 太远 | **3000 m** |
| 雾 near/far | size × 1.5 / 4.2 = 2400 / 6720 | 稍一退远就整片洗白 | **2500 / 9000** |

**更要紧的一个隐藏 bug：`size` 用了默认值 120**

`createTerrainWorld` 里 `size` 读的是 `currentOptions.size`，而那是
`DEFAULT_TERRAIN_OPTIONS` 的 **120**（海岛边长）。DEM 的 `sizeMeters`（1600）
只在后面建高度场时才合并进 options——**太晚了**。

后果是相机远平面按 120 算出 **960 m**，而地形有 1600 m 宽，于是地形被远裁剪面切掉。
自检里 `camera.far=960` 而角点投影 NDC 跑到 **15.6**，一眼能看出问题。
天空穹顶半径、雾、近远平面、取景包围盒全都依赖 size，所以它必须最先确定。

修好之后 world-smoke 从 46/64 直接涨到 **66/66**——因为拾取、悬停、标记那十几条
失败断言全是射线被远裁剪面截断的级联后果。

**移除海岛内容**

| 文件 | 移除内容 | 行数变化 |
|---|---|---|
| `heightField.js` | `createHeightField()`（程序化噪声生成器）与沙盘默认参数 | 490 → 261 |
| `scenery.js` | `createWater()`（整张平面水面，DEM 用不到） | 418 → 347 |
| `terrainMesh.js` | `SKIRT_DEPTH_FACTOR`（沙盘底座比例） | — |
| `cartoonTerrain.js` | 全部 `demField ? A : B` 分支、三个 `DEM_*` 常量、程序化高度场兜底 | — |
| `TerrainMapView.vue` | "程序化沙盘"开关、`terrainSource` 状态、降级分支 | — |

**关键设计决定：没有 DEM 时直接抛错，不再静默降级。**

```js
if (!currentOptions.demField?.data) {
  throw new Error('createTerrainWorld: 缺少 DEM 高度场…')
}
```

静默退回一个假地形，会让人以为看到的是真实地形。宁可炸。

**自检改造**：`terrain-smoke` / `world-smoke` 原本几乎全在测程序化路径（439 / 548 行），
改成 DEM 路径。平地与陡崖两个专项改用**合成数据**——它们测的是 `normalAt` / `slopeAt`
的纯数学行为，与数据来源无关，用合成数据判据反而更干净。

新增 `scripts/lib/dem-fixture.mjs`：三个自检脚本共用同一份 DEM 读取逻辑。
（本项目已在"同一个值抄两遍"上栽过多次，读取方式也不例外。）

顺带修掉一处**断言本身不可靠**的地方：world-smoke 找地形网格用的是
"顶点最多的带色非索引网格"。示意性聚落现在有近 1500 栋，顶点数已超过地形，
同一个启发式就悄悄挑错了对象，报出来的却是"统计口径不一致"，把人往错方向引。
改为按名字 `terrain-surface` 精确定位。

**自检**：70 + 66 + 17 + 45 + dev server 冒烟，全部通过；生产构建通过。

### 第 14 轮 · 一次"过度优化"的自我纠正（完成）

**起因**：发现 `slopeAt`（12.5 m 基线）会把窄陡坎平均掉——实测某处 16 m 内高程掉 43 m（约 70°），
而 `slopeAt` 只报 0.339（19°）。于是聚落的坡度过滤拦不住横跨陡坎的建筑。

**过程（六次反复，值得完整记下来）**

| 步骤 | 做法 | 结果 |
|---|---|---|
| 1 | 加"占地内高差"硬过滤，阈值 2.5 m | **411 栋全部被拒** |
| 2 | 查为什么 | 单位错：用 `heightScale`（含 1.5 倍放大）换算，等于把限制收紧 1.5 倍 |
| 3 | 改用真实高差，阈值仍 2.5 m | 仍 0 栋 |
| 4 | 量实际分布 | 428 个候选点里**最小占地高差 5.6 m**，中位 16.4 m——这片河谷没有天然平整地块 |
| 5 | 放宽到 14 m + 加候选位采样 | 只剩 101 栋（原 515 栋），近景几乎看不到房子——**密度被牺牲，这是退步** |
| 6 | 回到"只靠底面下延"、去掉过滤 | 密度恢复；但下延量按采样值自适应，虚高到 94 m，墙身被拉成竖板 |
| 7 | 下延量封顶 6 m | 仍不对 |
| 8 | **删掉自适应下延，回到固定的 −0.5 m** | 稳定：实测最大悬空 0.4 m |

**这一轮真正的教训：不要拿测量值去做自适应的几何修正。**

`relief` 是在某个网格分辨率下采四角得到的，它不是一个稳定的物理量。
用它去决定"墙身下延多少"，等于**把测量误差直接放大成视觉缺陷**——
在 384 网格上它报到 94 m，就真的画出了一片 94 m 高的竖板。

而 `b.y` 本身就是占地最低点，底面再低 0.5 m 就不会悬空，实测最大悬空只有 0.4 m。
**贴地用固定的小常量就够了，不需要自适应。**

顺带修掉两处：

- 聚落特写视角的相机太近太低（190/130/240），前景树被近裁剪面切断又被放大，
  画面上出现一片竖板状条纹——**看起来像建筑几何坏了，其实只是相机位置不对**。
  退到 (430, 320, 540) 后正常。
- `rotation` 被算了两遍（一次给占地检查、一次给落位），且两次的随机数不同，
  导致"检查用的朝向"与"实际写入的朝向"不是同一个值。已统一。

**最终状态**：聚落 1496 栋、淹没 0、陡坡 0；树与建筑冲突 0（最小间隙 7.4 m）；
地标 8/9 在范围内、贴地偏差 0.000000 m。

### 第 13 轮 · 水面贴图 + 补上自检的最大盲区（完成）

**修掉一个从未生效的功能**

`demWater.js` 里有着这样一段：

```js
let texture = null
if (typeof document !== 'undefined') {
  // createWaterTexture 需要 canvas；仅在浏览器里挂贴图，Node 预览时跳过
  texture = null          // ← 浏览器里也走这一行
}
```

于是河面**永远是一块纯色，水流贴图从未生效过**。而且这个几何是手写的非索引三角面，
**根本没有 UV 属性**——就算挂上贴图也铺不上去。两处一起修：

| 问题 | 修法 |
|---|---|
| 贴图恒为 null | 真正调用 `createWaterTexture`，按 DOM 是否存在决定创建与否 |
| 几何无 UV | 按世界 XZ 线性映射生成 UV，与 `position`/`color` 一起提交 |

**更重要的收获：找到并补上了自检的最大盲区**

`material is not defined` 这种**运行时错误，150 项自检全都没抓到**——
因为既有自检只覆盖程序化沙盘路径，DEM 专用模块
（`demField` / `demWater` / `landmarks` / `settlement` / `osmBuildings`）
**从未被真正构造过**，只被"能不能 import"检查过。

新增 `scripts/check-dem-path.mjs`：把真实地形这条链路完整跑一遍，
45 项断言覆盖高度场参数、经纬度换算、水面几何（含 UV）、地标落位、聚落布局、
OSM 建筑轮廓、以及色带在实际参数下的分布。已并入 `npm run check`。

**自检从 150 项扩到 195 项**（terrain 66 + world 67 + view 17 + DEM 路径 45）。

这条教训值得单独记：**"模块能加载"与"功能能跑"是两件事**。
只测 import 的自检会给出虚假的安全感——它检查的恰恰是最不容易出错的那一环。

### 第 12 轮 · 林建冲突：一个"看着有、实际没有"的问题（完成）

**起因**：聚落特写里看到树与房子互相穿插，像是树长在屋顶上。

**排查过程（这一轮的价值全在这里）**

| 步骤 | 做法 | 结果 |
|---|---|---|
| 1 | 目视判断"树长在屋顶上" | 疑似缺陷 |
| 2 | 给 `createForest` 加禁区支持，把建筑位置传进去 | 加了禁区，**树的数量一棵没少**（都是 5200） |
| 3 | 查为什么禁区没生效 | **名额在扫描途中就用满了 `maxCount`**，被排除的坑位不会被别处的树补上 |
| 4 | 把 `density` 从 0.62 降到 0.34，让名额用不完 | 排除掉 50 棵，禁区开始生效 |
| 5 | 想量化"还有没有树落在建筑里" | 发现 `createForest` **没暴露落点**，无法核对 |
| 6 | 导出 `layout`，补上定量审计 | **落在建筑占地内 0 棵、紧贴边缘 0 棵、最小间隙 13.3 m** |

**结论：第 1 步的目视判断是错的。**树与建筑本来就没有穿插，看到的"重叠"是低角度透视下
前景树挡住远处房屋形成的错觉。**如果我只凭那张图就去"修"，会改坏一个本来就正确的东西。**

真正的缺陷是排查过程中顺带发现的两个：

1. **禁区机制因名额上限而失效**——这是个真实的逻辑陷阱：只要 `maxCount` 会在扫描完成前用满，
   任何"跳过若干候选位"的过滤都会变成空操作。注释里已写明"密度刻意压低到名额用不完"及其原因。
2. **`createForest` 没有暴露落点**——工具能力缺口。近景里"树在房后"和"树在屋顶上"在静态图上
   几乎分不出来，没有落点数据就只能靠猜。现已导出 `layout`。

**这一轮再次印证了前几轮反复出现的教训**：
判据必须落在可量化的东西上。整个项目里我已经三次因为"看图/用过期参数"得出错误结论
（第 7 轮的假坐标偏移、第 8 轮的过期斜率、这一轮的不存在的穿插）。

**新增工具**：`scripts/dem/check-tree-vs-building.mjs`（林建冲突定量审计）

**自检**：150 项全通过；地标贴地偏差 0.000000 m；聚落 515 栋、淹没 0、陡坡 0；
树与建筑冲突 0；384² 档位合计 30.6 万面，在性能预算内。

### 第 11 轮 · 取景重新配平（完成）

第 10 轮加了纵向放大后，地形纵横比从 1600:355 变成 1600:532，原来的取景参数不再合适：
目标点偏低、底座占掉画面大半。本轮把三处一起配平：

| 参数 | 旧值 | 新值 | 理由 |
|---|---|---|---|
| `DEM_CAMERA_OFFSET` | `[0.62, 0.4, 0.86]` | `[0.62, 0.48, 0.86]` | 俯角约 29°→26°；抬高目标点后俯角可略降，地形起伏更可读 |
| `DEM_TARGET_HEIGHT_FACTOR` | 沿用沙盘 0.35 | **0.46** | 目标点相对放大后的地形偏低，画面下缘被底座吃满 |
| `DEM_SKIRT_FACTOR` | 0.16 | **0.1** | 底座再收薄一档；它只是"托盘的厚度"，不该与地形争视觉重量 |
| `fill` | 0.985 | 0.93 | 贴边太紧，留一点呼吸 |

同时修掉一处**取景与重置视角不一致**的隐患：`defaultTarget()` 里仍硬编码
`SCENE_LOOK.targetHeightFactor`，于是"重置视角"会把镜头拉到一个与初始取景不同的高度，
画面会跳。现在两处共用同一个系数。

**结果**：地形居中、山体结构可读、底座不再抢戏。

**自检**：150 项全通过；色带分布不变（所有地形色带均有出现）；

### 第 10 轮 · 纵向放大（含一次危险的副作用与修正）

**问题**：低角度视角下地形明显平缓，看不出实拍里"夹江峡谷"的陡峭感。
根因是 30 m 分辨率的公开 DEM 把陡崖抹平了——实测平均坡度约 12°、最大 51°，
而实拍照片里的谷壁约 18–25°。这是分辨率的固有代价，不是数据错。

**做法**：新增 `verticalExaggeration`（默认 1.5），作用于 `heightScale`。
**数据里存的仍是真实米值**，元数据 `elevation` 不受影响——放大只发生在渲染参数上。
这是一个明确的视觉取舍，代码注释里写清了。

**危险副作用（本轮最重要的发现）**

放大系数同时被 `normalAt` 用来算坡度，于是**坡度也放大了 1.5 倍**：

| 色带 | 正常 | 放大后 |
|---|---|---|
| rock | 7.0% | **20.5%** |
| cliff | 0.6% | **3.5%** |
| forest | 47.9% | **37.7%** |

山体表面被大面积涂成裸岩。**视觉放大不该改变"这里长什么"这个判断**——
附属物分类是关于真实地形的事实，不是关于渲染的。

修法：`createHeightFieldFromData` 增加 `slopeSpan`（不含放大），
`normalAt` 一律用它算坡度；只有几何的 `worldHeight` / `waterY` 用放大的 `heightScale`。
同时给 `pickBand` 传真实高差，让"水面下 4 m 算深水"的换算不受放大影响
（修正后 deepWater 从 0.52% 升到 0.83%）。

**第二次踩同一个坑：预览脚本又硬编码了参数**

预览脚本自己写了 `heightScale: demMeta.elevation.span` 等三个值，
所以应用侧加了放大系数，**预览却纹丝不动**（出图哈希与上一轮完全一致），
等于拿一张过期的图做判断。已改成 `...demTerrainOptions(demMeta)`。

这已经是本项目第三次栽在"同一份参数存在两个出处"上（前两次见第 7、8 轮）。
规律很清楚：**只要有一个值被抄了第二遍，它迟早会与正本不一致，而且不一致时不会有任何报错。**

**底座厚度的基数**：底座改为以**真实高差**为基数（`skirtDepthOf`），
而不是 `heightScale`。否则放大系数会把底座一起加厚，地形又被压成薄饼。

**遗留**：纵向放大改变了地形纵横比，取景参数需要重新配平（下一轮处理）。

**自检**：150 项全通过

### 第 7 轮 · 条纹溯源与水系校验（完成，含一次自我纠错）

**成果一：俯视图的"规则条纹"是渲染器漏像素，不是地形问题**

之前好几轮我都在怀疑那些条纹是高程伪影，改了抖动、改了水位都无效。这轮定位到了真正原因：

软件光栅器只测试"像素中心是否严格落在三角形内"。地形是密铺三角面、相邻面共享边，
共享边两侧的像素会被两个面同时判为外部，于是整张图出现规则缝隙网格。
修法是包围盒外扩 1 像素 + 重心坐标容差；重叠部分由深度测试裁决。

顺带量化了另一项噪声：逐面明暗抖动 `jitter=0.075` 是给程序化低多边形调的，
真实 DEM 用不着它。实测同一张俯视图的 PNG 体积 **116 KB → 29 KB**（关掉抖动后），
胀出来的全是伪信息。DEM 模式已改为 0.015。

**成果二：逐面抖动与色带判据的定位**

**成果三（最重要）：一次被代理判据带偏的诊断，以及纠正**

| 步骤 | 做法 | 结论 |
|---|---|---|
| 1 | 从瓦片影像里"找蓝色像素"当水面真值 | ✗ 失败：OSM 的黄色公路也满足 `b > r`，整条 S216 被当成河，IoU 6.6% |
| 2 | 改用 OSM 水系**矢量**做真值 | ✓ 干净：`waterway=river` 是权威位置 |
| 3 | 发现地形水面与 OSM 河道是"两条平行斜线" | 疑似整体错位 250–330 m |
| 4 | 用"地标应落在低处且平缓"搜坐标偏移 | 搜到 dx=−300 / dz=−375（约 480 m），**看起来像 GCJ-02 偏移** |
| 5 | 验证该偏移能否让水系对齐 | ✗ 命中率反而从 33% 掉到 0——河道被推出场景 |
| 6 | 改用硬判据：OSM 水系必须落在地形谷底 | 最优平移只把命中率从 33% 提到 **35%**，无实质改善 |
| 7 | 逐点比对河道高程 vs 垂直方向局部最低点 | ✓ **河道比最低点仅高 10.3 m，3/3 点在 40 m 内——OSM 河道位置正确** |

**结论：不存在坐标系偏移。** 第 4 步的推断是错的，原因是**代理判据被优化器利用了**：
"地标应落在低处且平缓"这个要求，场景里最平最低的地方恰好是河边一大片砾石滩，
往那一挪分数自然涨，但那是个假解。**弱判据做搜索，会把解带到判据的极值处，而不是真值处。**

低 IoU 的真正原因是**测量方法本身的缺陷**：
- 河是**线状**地物，我用 4 格（约 17 m）稀疏采样，一条细斜线在两侧的采样点很难重合
- 两侧的"水"概念宽度不同：OSM 河道是 12 m 半宽的中心线，地形水带最宽能到 100 m

**这一轮的价值不在产出了什么，而在于避免了一次错误的全局改动**——
如果按第 4 步的结论把所有坐标整体挪 480 m，地形会彻底错位，而且因为"看起来还在场景里"，
这种错误极难被发现。

**新增工具**（累计 21 个诊断脚本）

| 脚本 | 用途 |
|---|---|
| `check-stripes.mjs` | 剖面自相关，判断规则纹理是真实地貌还是数值伪影 |
| `check-ortho-match.mjs` | 正射图与真实影像并排对照 + 水面 IoU |

**街巷轴向的两次纠正（值得记下）**

1. 最初用**地标做 PCA** 求主轴 → 得到的方向与河流近乎垂直，房子会横跨河道。
   原因：地标分布受"景点密度"影响（道观在山腰、广场在镇北），不代表聚落走向。
2. 改用**水体 PCA** → 被寿溪湖带偏。湖是一大团近似圆形的点，把协方差主轴拽向自己。
3. 最终用**谷底脊线**：沿高度带切片、每片取最低点，再对脊线做直线拟合。
   谷底脊线不依赖水体形状，只依赖"哪里最低"这个地形事实，稳定得多。

**聚落中心的定位原则**：**地标群决定聚落的位置，河谷只决定街巷的朝向**。
中途试过"从脊线推到地标一侧"，结果聚落整体跑到西北角、大半地标落在街区外——
因为一旦中心被推到脊线上，340 m 的生成半径就够不到真正的地标群了。

**踩过的坑**：`eachFace` 的回调签名是 `(a, b, c, n, albedo)`，第三个参数 `c` 是三角形
第三个顶点，不是颜色。预览脚本里把它当 albedo 用，整片镇子渲染成纯黑
（顶点对象当 THREE.Color 读，分量全是 undefined）。数学单独验算时一切正常，
只有渲染出来才暴露——这类错误必须靠出图发现。

**新增视图**：预览脚本增加 `settlement` 视角（低空斜视聚落）与 `top` 纯色带俯视

### 5.1 已踩过的坑（勿重复）

| 坑 | 现象 | 应对 |
|---|---|---|
| rolldown 的 `manualChunks` | 对象形式直接构建失败（`manualChunks is not a function`） | 只能用函数形式 |
| PowerShell 5.1 编码 | `Set-Content -Encoding UTF8` 带 BOM，读回中文可能花屏 | 注意 BOM；用 read 工具核对而非靠控制台显示 |

| 按需导入的 dev 请求风暴 | element-plus 子模块请求过多 | `optimizeDeps.include` 预打包 |
| unplugin 生成的类型声明 | 被生成到 `src/types/` | 需提交进仓库，并在 `jsconfig.json` 的 `include` 中声明 |
